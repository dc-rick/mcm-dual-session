# 双会话协议 · 详细规范

本文件是 `SKILL.md` 的展开。只在需要判断边界、处理争议、恢复状态时读；日常执行看 `SKILL.md` 和任务单即可。

---

## 1. 设计前提

### 1.1 两个会话，不是两个 subagent

subagent 与主会话共享同一套文件、同一个上下文来源，审查者容易继承执行者的假设。这里要的是**两个独立启动的 Claude Code 会话**：

- 各自独立的上下文窗口，互不继承推理过程；
- 同一个仓库，但写权限按目录切开；
- 只通过磁盘文件交接，不通过聊天消息；
- 用户是唯一的调度者和最终决策人。

如果实际只有一个会话，就不要假装双会话；在回复里明确“这是单会话自查，独立性弱于双会话冷读”。

### 1.2 文件是唯一状态源

聊天记录会丢、会被压缩、会被摘要改写。台账、任务单、交付 JSON 是可 diff、可追溯、可被第三方复核的。任何“上次说好了”的内容，如果没有落进文件，就等于没发生。

### 1.3 审查者不拥有执行者的文件

这是整个协议最重要的一条。审查者一旦动手改代码/论文，就失去了“独立复核”的位置：他会不自觉地为自己刚写的改动辩护。要改，就下任务；要示范，就写进任务单的“修法”列，不直接改文件。

## 2. 角色与边界

### 2.1 指导方（审查/规划）

职责：

- 读题、拆问、定优先级；
- 发现问题，登记问题台账；
- 写任务单，定义可验收的标准；
- 冷读交付，复算/复跑，给通过或退回；
- 维护三本台账；
- 向用户提出需要拍板的决策。

可写：

- `审查与规划/任务单/`
- `审查与规划/审查记录/`
- `审查与规划/台账/`
- 其他 `审查与规划/` 下的规划文档

只读：

- `code/`、`paper/`、`data/`、`交付/`
- 仓库根文档、`.claude/`、`.git/`

明确禁止：

- “我顺手把这个 typo 改了。”
- “我直接跑一下模型看看。”
- “我在论文里补一句说明。”
- “台账我先按通过写，等执行方确认。”

### 2.2 执行方（代码/论文/数据/交付）

职责：

- 按任务单执行；
- 在授权目录内写代码、跑实验、改论文、出图；
- 跑验收检查，留证据；
- 写交付 JSON；
- 如实报告失败、边界、无法复现项。

可写：

- `code/`
- `paper/`
- `data/runs/T00x/`（新运行）
- `交付/`

只读：

- `data/` 中已有输入文件
- `审查与规划/`
- 仓库根文档（除非任务单明确授权）

明确禁止：

- 改 `审查与规划/` 里的任何文件，包括台账状态。
- 覆盖 `data/` 已有输入或旧 `results/`。
- 在交付里把失败写成“基本通过”。
- 未经任务单授权改论文结论或数字。

### 2.3 用户（principal）

- 决定优先级、时间预算、口径选择（例如 p 取 0.128 还是 0.185）。
- 在两个会话之间转交消息。
- 批准跨边界操作（例如让执行方临时改一个规划文档）。
- 对“是否接受某个不利结论”做最终决定。

用户的口头指示要落进决策台账才生效；聊天里的“可以”不构成对执行方的长期授权。

## 3. 任务生命周期

```
待执行
  │  执行方接单
  ▼
执行中 ──阻塞──► 阻塞 ──用户/指导方解除──► 执行中
  │
  │  交付 JSON
  ▼
已交付
  │  指导方验收
  ├──通过──► 通过（终态）
  └──退回──► 退回 R1 ──执行方返工──► 执行中（R1）
```

特殊终态：

- `取消`：任务不再需要；在验收结论里写原因。
- `出局`：被时间预算砍掉；在验收结论里写“未做，原因”。
- `部分完成`：不单独设状态；用 `已交付` + `notes` 说明哪几项没做，指导方决定是否拆新任务。

### 3.1 任务编号

- 格式 `T` + 三位数字，从 `T001` 起。
- 返工不新开号，用同一编号 + `revision: R1`、`R2`。
- 任务单文件名：`T00x_短标题.html`。
- 交付文件名：`T00x_delivery.json`；返工覆盖同一文件，`revision` 递增，旧版本由 git 保留。
- 验收记录：`T00x_验收_YYYY-MM-DD.html`；同一任务多次验收加 `_R1`。

### 3.2 任务单必须回答的十个问题

1. **为什么做**：对应哪个问题/决策，不做会怎样。
2. **做什么**：一句话目标。
3. **不做什么**：明确的 out of scope，防止顺手扩大。
4. **允许写哪些文件/目录**。
5. **输入是什么**：数据、参数、上游结果、文献。
6. **输出是什么**：文件路径、格式、必须包含的字段。
7. **验收标准**：编号、可执行或可检查。
8. **证据要求**：命令、日志、复算口径。
9. **优先级/截止**：相对时间或 DDL。
10. **回滚**：改坏了怎么恢复（commit、备份、重跑）。

缺第 4、7、8 项的任务单不合格，执行方应退回要求补齐。

### 3.3 验收标准的写法

好：

- `grep -rn "ten days" paper/*.tex` 命中 0。
- `python -I code/95_numbers.py` 输出中 `fleet = 495540`，与 `data/runs/T001R2/fleet.json` 一致。
- 表 5 的 5 个 `Trips per user` 值与 `data/runs/T016/table5.csv` 逐值相等。
- xelatex 两遍：undefined 0、overfull 0、正文 ≤25 页。

坏：

- “数字要一致。”
- “论文读起来通顺。”
- “模型合理。”
- “参考一下优秀论文。”

每条验收标准最好能对应交付 `checks` 的一个键；不能对应的，说明为什么只能人工判断。

## 4. 交付契约

### 4.1 必填字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `task` | string | 任务编号，必须与文件名一致 |
| `title` | string | 任务标题 |
| `date` | string | `YYYY-MM-DD` |
| `status` | string | `delivered` / `blocked` / `partial` / `accepted_r1` … |
| `summary` | string | 一段话：做了什么、结果是什么、是否达到验收 |
| `checks` | object | 验收项 → 证据；键与任务单编号对应 |
| `outputs` | array | 产出文件路径（相对仓库根） |
| `notes` | array | 未解决项、边界、假设、无法复现项 |

### 4.2 强烈建议字段

| 字段 | 说明 |
|---|---|
| `revision` | `R0`、`R1`… |
| `affected` | 改动清单：`location` / `old` / `new` / `basis` |
| `integrity` | `readonly_respected`、`no_files_written_in_review_or_planning` |
| `commands` | 实际执行的命令与退出码 |
| `inputs` | 输入文件 + 哈希/版本 |
| `blocking_question` | 仅 `blocked` 时：需要谁回答什么 |

### 4.3 `checks` 的证据粒度

每个值至少包含以下之一：

- 命令 + 退出码 + 关键输出（可截断，但要能定位）；
- 文件路径 + 行号 + 实际值；
- 独立复算的公式 + 输入 + 结果；
- 对比基线（commit、旧文件、旧结果）的 diff。

反例：

- `"1": "pass"` —— 无法复核。
- `"all_good": true` —— 没有对应验收项。
- `"note": "应该没问题"` —— 不是证据。

### 4.4 `affected` 的写法

```json
{"location": "paper/sec5_q2.tex:88", "old": "K = 60", "new": "K = 40", "basis": "data/runs/T007/q2_results.json: obj(40)=... < obj(60)=..."}
```

- `old` 必须能在旧版本/旧稿里找到；`new` 必须能在当前文件里找到；`basis` 必须是可打开的文件或可重跑的命令。
- 只写“文字调整”的条目也要列，方便指导方确认没有夹带数字变化。
- 如果改动很多，按文件分组，不要逐字列。

### 4.5 失败与阻塞

- 验收项失败：`status` 不能是 `delivered`；用 `partial` 或 `blocked`，在 `checks` 里写失败证据，在 `notes` 里写影响。
- 缺少用户决策：`status: blocked`，`blocking_question` 写“需要用户决定 X；选项 A/B 的后果是…”。
- 缺少外部数据：`status: blocked`，写清已尝试的来源和失败原因；不要编造替代数据。

## 5. 验收契约

### 5.1 独立性

指导方验收时不能只读交付的 `summary`。至少做：

1. 打开一个产出文件，亲眼确认内容；
2. 从结果文件复算一个关键数字；
3. 跑一条任务单里的验收命令；
4. 检查 `git status` / `git diff` 的范围。

如果指导方发现自己需要“改一下才能验”，停下来：这说明任务单或交付不合格，退回，不要自己修。

### 5.2 通过的条件

- 所有 `高` 优先级验收项通过；
- 所有关联的 `高` 问题已关闭或有明确的“不修”理由；
- 论文数字与结果文件一致（抽查至少 3 个，含 1 个本次改动的数）；
- 没有越界写入；
- 失败/边界项已如实记录，且不影响结论。

### 5.3 退回的写法

退回不是“再改改”，而是一张新的缺陷单：

```text
R1 缺陷
1. [高] 表 5 的 5 个值仍来自旧结果；证据：...；修法：...；复验：...
2. [中] `notes` 未说明 172 个干涸格子的口径；修法：...；复验：...
```

每条给：严重程度、证据、修法、复验标准。不要只说“不一致”。

### 5.4 验收记录

`审查与规划/审查记录/T00x_验收_YYYY-MM-DD.html` 至少包含：

- 任务编号、验收日期、验收人（指导方会话）；
- 读了哪些文件；
- 复算了什么、命令、结果；
- 与交付自报值的差异；
- 通过/退回结论；
- 未解决项与后续任务编号。

## 6. 台账契约

### 6.1 任务台账

表头（与本项目现有文件一致）：

```csv
编号,标题,对应问题,执行方,下达日期,前置条件,状态,任务单,交付物,验收日期,验收结论
```

- `对应问题`：问题台账编号，多个用 `；` 分隔。
- `前置条件`：依赖的任务/决策，例如 `T001 通过；B6=封闭车队`。
- `状态`：见 §3。
- `交付物`：相对路径，多个用 `；` 分隔。
- `验收结论`：一段话，写“复算了什么、结果如何、还有什么没解决”，不要只写“通过”。

### 6.2 问题台账

```csv
编号,发现日期,严重程度,标题,证据,影响,修法,验收标准,负责方,关联,状态,关闭日期,关闭证据
```

- `证据`：文件:行、命令输出、数据、题面原文。没有证据的问题不立项。
- `影响`：对结论/可信度/合规的具体影响，不写“可能有问题”。
- `修法`：可执行的动作，不写“加强论证”。
- `验收标准`：可检查的条件。
- `关联`：任务编号、决策编号、其他问题编号。
- `关闭证据`：验收记录路径 + 复算结果。

严重程度定义：

- `高`：改变结论、违反题面、评委一眼能抓的自相矛盾、数据/物理上不可能。
- `中`：可信度受损、缺少验证、口径不一致、图表误导。
- `低`：文字、版式、引用格式、可读性。

### 6.3 决策台账

```csv
编号,决定事项,审查方建议,理由,影响到,提出日期,状态,用户决定,决定日期
```

- 只登记**需要用户拍板**的事，不登记执行细节。
- `审查方建议` 是建议，不是决定；`用户决定` 才是。
- 决定改变后，旧行不删，状态改 `已撤销`，新开一行或追加说明。
- 与任务关联：`影响到` 写任务编号/章节。

### 6.4 台账维护规则

- 只有指导方写。
- 每次验收后立即更新，不攒批。
- 编号不复用；不删行；不改历史日期。
- 状态词保持可枚举；自由文本放 `验收结论` / `关闭证据`。
- 台账是给人读的，也是给脚本读的：不要合并单元格、不要多行字段、不要用全角逗号当分隔符。

## 7. 数字与证据

### 7.1 数字来源

论文/报告里的每个数，必须能追到：

1. 结果文件（`.json`、`.csv`、`.mat`、`.npz`）；
2. 生成它的脚本 + 命令；
3. 脚本读的输入数据 + 版本/哈希。

链子断了，这个数就不能用。指导方验收时抽查；执行方交付时主动给路径。

### 7.2 重提机制

每次仿真/模型改动后：

1. 重跑结果生成脚本；
2. 重跑数字提取脚本（如 `code/95_numbers.py`）；
3. diff 旧/新数字日志；
4. 把变化写进 `affected`；
5. 论文里所有引用同一量的地方一起改。

不允许“我记得是 3.4×10⁵”或“摘要先不改”。

### 7.3 无法复现的数

- 标 `unreproducible`，写清为什么（缺输入、随机性、外部服务、旧代码未保留）。
- 能从论文删就删；不能删就降级为“文献值/假设值”，并给区间。
- 不要用“约”“左右”掩盖一个本该精确的数。

### 7.4 不确定性的来源

交付里如果给区间，标明来源：

- 识别参数（拟合/估计）；
- 假设负荷（情景设定）；
- 文献值（引用）；
- 数值/随机误差（种子、样本）。

三类混在一起时，拆开写，不要只给一个总区间。

## 8. 冲突与升级

### 8.1 执行方不同意任务单

- 不要默默按自己的理解做。
- 交付 `status: blocked`，`blocking_question` 写：任务单第 X 条与第 Y 条冲突/不可执行，建议改为…，影响是…。
- 指导方决定：改任务单、拆任务、或维持原样并说明理由。

### 8.2 指导方与执行方对数字不一致

- 以可复现的结果文件为准，不以任何一方的记忆为准。
- 指导方复算值写入验收记录；执行方在 R1 交付里回应差异。
- 差异无法消除时，升级到用户，登记决策台账；不要“取平均”或“选好看的那个”。

### 8.3 用户改变口径

- 先登记决策台账（新行或更新旧行），写清影响到的任务/章节。
- 再下新任务或返工任务；不要在聊天里口头改完就继续。
- 已经验收的数字如果受口径影响，重新打开相关问题，不要假装没发生。

### 8.4 时间不够

- 指导方按 DDL 砍任务，在任务台账写 `出局` + 原因。
- 砍掉的验证/敏感性分析，在论文局限性里如实写，不要用“未来工作”掩盖。
- 不要为了赶时间跳过验收；宁可少做一个任务，不要交一个没验的数。

## 9. 压缩、重启、换会话

### 9.1 恢复顺序

1. 角色（问用户或读会话摘要；不确定就问）。
2. `.dual-session/config.json`（路径覆盖）。
3. 任务台账：最后 5 行 + 所有非终态行。
4. 问题台账：所有非 `关闭` 行。
5. 决策台账：所有 `待定` 行。
6. 最新交付 JSON + 对应验收记录。

### 9.2 恢复后的第一条回复

必须包含：

- 角色与边界；
- 当前开放任务及状态；
- 最近一次交付/验收；
- 下一步动作；
- 如果发现文件与摘要冲突，明确指出。

### 9.3 不要做的事

- 不要根据摘要直接继续写代码/论文，而不读台账。
- 不要假设“上次说到哪”就是文件里的状态。
- 不要把旧交付 JSON 当成当前状态；看 `revision` 和日期。

## 10. 反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 指导方顺手改论文 | 失去独立性，验收变成自验 | 写任务单 |
| 执行方更新台账 | 状态失真，无人对结论负责 | 交付里写 `notes`，指导方落账 |
| 交付只有 summary | 无法复核 | `checks` 带命令/文件/值 |
| 验收只看自报 | 错误通过 | 至少复算一项 |
| 任务单没有 out of scope | 范围蔓延 | 明确“不做什么” |
| 任务单验收标准不可执行 | 争议无法收敛 | 编号 + 命令/文件/阈值 |
| 数字从记忆来 | 论文与结果脱节 | 从结果文件重提 |
| 失败藏在 notes 里 | 结论被高估 | `status: partial/blocked` |
| 台账删行/改历史 | 审计链断裂 | 追加 + 状态变更 |
| 单会话冒充双会话 | 虚假独立性 | 明确说明 |
